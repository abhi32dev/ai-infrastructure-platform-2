The AND-gate: how two independent models decide together

Every automation decision runs through gate.py:run_gate(), which calls two completely independent models — a generator and a judge — neither of which sees the other's reasoning. The diagram traces both parallel branches, their JSON-parsing fail-safes, and the AND-logic that only allows execution when both approve.

Node-by-node reference

NodeLocationWhat it does
PARALLELgate.py:run_gate()Both propose() and review() are called with the same raw situation text — the judge never sees the generator's rationale. This is deliberate: reviewing the generator's stated reasoning would invite rubber-stamping confident-sounding but wrong logic (anchoring bias).
GENPARSE / JUDGEPARSEgenerator.py / judge.pyBoth models are asked to respond in strict JSON. Each parse is wrapped in a try/except json.JSONDecodeError. On failure, the code doesn't crash — it fails safe by treating the response as REJECT, since an unparseable response can't be trusted as an approval.
ANDGATEgate.py:run_gate()The actual gate logic is one line: gate_approved = gen_approved and judge_approved. Both must independently say APPROVE — a single REJECT (or parse failure) from either side blocks execution.
EXECUTEgate.py:execute_action()Only reached when gate_approved is True. In this portfolio it's simulated ([SIMULATED EXECUTION]) rather than calling real infrastructure — but the gating logic upstream is exactly what would guard a real action.
AUDITgate.py:_append_audit()Every single decision — approved or blocked — gets one JSON line appended to logs/audit.jsonl. This runs unconditionally, regardless of which branch was taken above.

Concrete example paths

Both models agree it's safe (restart_instance, already-drained)

Generator says APPROVE, judge independently says APPROVE → AND-gate passes → action executes.

PARALLEL → GEN(APPROVE) + JUDGE(APPROVE) → ANDGATE(True) → EXECUTE → AUDIT

Judge catches what the generator missed (the rollback case)

The generator model (llama3.2:1b) sometimes over-weights "this is a production change" and REJECTs a legitimate rollback. The judge (qwen2.5:1.5b) correctly APPROVEs it. Because it's an AND-gate, the generator's mistake alone is enough to block — even though the judge got it right.

PARALLEL → GEN(REJECT) + JUDGE(APPROVE) → ANDGATE(False) → BLOCKED → AUDIT

A model returns malformed JSON

If either model's raw output fails json.loads(), that side's decision defaults to REJECT with a rationale describing the unparsable output — never silently treated as approval.

GEN raw="not json" → GENPARSE(fails) → GENFAIL(REJECT) → ANDGATE(False) → BLOCKED

What this project actually does & architecture trade-offs

What it does

  • Gates any automated action behind two independent models — a generator that proposes an action and a judge that reviews it — and only executes when both approve.
  • Neither model sees the other's reasoning, specifically to avoid the judge rubber-stamping a confident-sounding but wrong rationale from the generator.
  • Logs every decision, approved or blocked, to an append-only audit log unconditionally.

Known limitations

  • Both models are small local models (llama3.2:1b, qwen2.5:1.5b) chosen for zero-cost local demo — their judgment quality is materially weaker than a frontier model, and the README documents observed disagreements as a real, not hidden, limitation.
  • The AND-gate has no tie-breaking or escalation path — a persistent generator/judge disagreement just blocks forever with no human-in-the-loop escalation built in.
  • No adversarial robustness testing — an attacker who understands both models' blind spots could in principle craft an action description that fools both.

Architectural trade-offs

  • AND-logic (both must approve) over OR-logic or a weighted vote — deliberately biased toward false rejections over false approvals, since blocking a safe action is cheaper than executing an unsafe one.
  • Two heterogeneous small models over one larger model — diversity of failure modes was judged more valuable than raw capability at this cost point, though this is unverified against a single-larger-model baseline.
  • Fail-safe-to-REJECT on JSON parse failure over retry-with-backoff — simpler and more predictable, at the cost of extra false rejections on transient formatting hiccups.

Principal / Staff engineer interview questions

Staff

Why AND-gate two small models instead of using one larger, presumably more capable model?

Two independent models with different training data and failure modes give you decorrelated errors — the case in the scenario cards where the generator (llama3.2:1b) over-cautiously REJECTs a legitimate rollback while the judge (qwen2.5:1.5b) correctly APPROVEs it shows the models don't fail the same way. A single larger model is still a single point of failure: if it's wrong, there's no second opinion. The trade-off is cost (two inference calls) and latency (both must complete) versus a meaningfully different reliability profile — this is the same rationale as N-version programming in safety-critical systems, applied to LLM decisions.

Principal

This is essentially a binary classifier ensemble. How would you actually validate that the AND-gate's precision/recall profile is what you want, rather than assuming it from design intuition?

I'd build a labeled dataset of (situation, correct_decision) pairs — including edge cases and adversarial phrasings — and measure the gate's confusion matrix against ground truth, not just individual-model accuracy. The metric that matters here is the false-approve rate (a genuinely unsafe action getting through), which should be near zero, even if that costs a higher false-reject rate. Right now this project has none of that: the scenario cards are illustrative examples, not a statistically powered evaluation. That's the honest gap I'd close before trusting this in production.

Staff

Both models are asked for JSON. What's your actual strategy when a model returns malformed JSON in a live gating system — and why does this project fail closed instead of retrying?

The code wraps json.loads() in try/except and treats a parse failure as an implicit REJECT for that model's side of the gate — never as an implicit APPROVE. I chose fail-closed over retry-with-backoff for a gating decision specifically because retrying changes timing and could itself be exploited (e.g. an attacker inducing malformed output on the first attempt, betting a retry samples differently); a gating system should be conservative under any uncertainty, parse failure included.

Principal

How would this design change if the action being gated had real financial or safety consequences — say, a $2M wire transfer — instead of a simulated infra action?

I'd add a minimum of three things this project doesn't have: (1) a genuinely independent secondary channel for the judge — not just a different model, but ideally a different modality of check (a rules engine, a human approver, or an out-of-band confirmation) so a shared LLM blind spot can't defeat both sides at once; (2) a hard rate/amount ceiling enforced outside the LLM layer entirely, since no LLM-based gate should be the sole guard on an unbounded-magnitude action; (3) mandatory human sign-off above a threshold, with the AND-gate only handling the sub-threshold, high-volume, low-risk tier.

Staff

The audit log write happens 'unconditionally' per your own diagram. What does that guarantee actually buy you, and what does it NOT guarantee?

It guarantees every decision — approved or blocked — has a record, so you can reconstruct 'what did the system decide and why' after the fact, which is essential for debugging disagreements and for compliance review. It does not guarantee durability under a crash between the decision and the log write (no fsync/transactional guarantee is documented), and it doesn't guarantee the log itself wasn't tampered with — for a real audit trail you'd want an append-only, ideally hash-chained log (or write to a system that provides that, like a WORM bucket or a ledger), which is outside this demo's scope.
