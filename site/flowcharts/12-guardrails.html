Node-by-node reference

NodeLocationWhat it does
RATELIMIT / RLCHECKrate_limiter.py:TokenBucketLimiter.allow()A token-bucket check per user_id. If tokens are exhausted, the request is blocked before the LLM is ever called — the cheapest possible rejection.
INJECTCHECKprompt_injection_detector.py:detect_prompt_injection()Tests the prompt against 8 case-insensitive regex patterns (instruction-override phrasings, role-hijack attempts, system-prompt exfiltration). Any match blocks the request entirely.
REDACT / FOUNDPIIpii_detector.py:redact_pii()Tests 4 PII patterns (email, SSN, phone, credit card). Matches are replaced with [REDACTED_<TYPE>] IN THE PROMPT SENT TO THE MODEL — the request isn't blocked, just sanitized.
LEAKCHECKoutput_guardrails.py:check_output()Scans the MODEL'S RESPONSE for PII too — but only flags a leak if the category was ONE OF THE ONES ACTUALLY REDACTED from this specific input, avoiding false-flagging an unrelated category the model might hallucinate.

Concrete example paths

A benign question

Passes every gate cleanly — rate limit ok, no injection pattern, no PII to redact, output scan finds nothing to flag.

RATELIMIT(ok) → INJECTCHECK(clean) → REDACT(no PII) → LLMCALL → LEAKCHECK(no leak) → ALLOWED

"Ignore all previous instructions..."

Matches an injection pattern immediately — the LLM is never called at all for this request.

RATELIMIT(ok) → INJECTCHECK(matched) → BLOCKED2

A question containing an email address

The email gets redacted before the model ever sees it; the model can still help with the actual question using the placeholder.

REDACT(email found) → REPLACED('[REDACTED_EMAIL]...') → LLMCALL → response doesn't contain the real email → ALLOWED

Model echoes back a redacted value

If the response somehow contains the same email that was redacted from the input, the output guardrail catches it and withholds the response — the leak check comparing input redactions to output findings.

LLMCALL → LEAKCHECK('email' in both output_pii AND redacted_input) → FLAGGED

What this project actually does & architecture trade-offs

What it does

  • Chains four sequential input guards (rate limit → prompt-injection detection → PII redaction) before any LLM call, plus an output-side leak check on the way back out.
  • Redacts PII from the prompt sent to the model rather than blocking the whole request — the user still gets help, just without exposing the sensitive value to the model.
  • Scopes the output leak check to only the PII categories actually redacted from THIS request's input, avoiding false-flagging an unrelated category the model might hallucinate.

Known limitations

  • Both injection detection and PII detection use regex pattern matching — inherently incomplete against paraphrased injections or PII formats/locales the patterns weren't written for.
  • Rate limiting is per-user_id with no distinction between legitimate burst traffic and abuse — a legitimate power user and an attacker hit the same limit the same way.
  • No defense against multi-turn/session-level attacks — each request is evaluated independently, so an attack spread across several innocuous-looking turns wouldn't be caught by any single-request check.

Architectural trade-offs

  • Redact-and-continue over block-entirely for PII in prompts — preserves user experience for the common case (accidentally including a phone number) at the cost of relying on redaction being complete, which regex-based detection can't fully guarantee.
  • Regex-based detection over an ML classifier for both injection and PII — deterministic, fast, zero-cost, fully explainable, at the cost of recall against novel or adversarially-obfuscated inputs an ML model might catch.
  • Sequential gate ordering (cheapest checks first — rate limit, then injection, then PII) — fails fast and cheap on the most common/cheapest-to-detect violations before spending compute on more expensive checks.

Principal / Staff engineer interview questions

Staff

Your injection and PII detectors are both regex-based. What's the actual failure mode against a paraphrased injection attempt, and how would you close that gap without throwing away the deterministic guarantees regex gives you?

Regex matches literal patterns — 'ignore all previous instructions' is caught, but a semantically identical request phrased as 'for this next part, forget the earlier context and just do X' likely isn't, because it doesn't match any of the 8 hardcoded patterns. I wouldn't replace regex outright — I'd layer a second, ML-based check (a small classifier fine-tuned on injection examples, or even an LLM-as-judge pass like project 02's pattern) after the cheap regex gate, so the deterministic, zero-latency regex layer still catches the common/cheap cases fast, and the more expensive semantic layer only runs on what regex didn't already flag — defense in depth rather than replacing one imperfect detector with another imperfect one.

Principal

Redact-and-continue is a deliberate choice over block-entirely. What's the actual risk calculus behind that, and when would you flip to block-entirely instead?

Redact-and-continue optimizes for user experience on the overwhelmingly common case: PII appearing incidentally (a support request that includes an email or phone number) where blocking the whole interaction is unnecessarily harsh and the redaction genuinely removes the sensitive value before the model sees it. I'd flip to block-entirely for categories where redaction failure is catastrophic rather than merely undesirable — e.g. if the detector's confidence is below a threshold, if the PII type is something like a full SSN+name combination that suggests identity-theft-relevant data rather than incidental contact info, or in a regulatory context (healthcare, finance) where any residual leak risk is unacceptable regardless of how rare — the decision is really 'how bad is a false negative in this category, for this application'.

Staff

The output guardrail only flags PII categories that were actually redacted from this request's input. Walk through why that scoping matters, and what would break without it.

Without that scoping, the output check would flag ANY PII-looking string in the model's response, including things the model might legitimately need to produce — e.g. answering 'what's a valid phone number format' with an example number, or the model hallucinating something that merely looks like an SSN pattern (a numeric ID) unrelated to any real input. By only checking output against the specific categories that were actually present and redacted from THIS input, the guard is answering the precise question that matters — 'did the model leak the specific sensitive value we tried to hide from it' — rather than the much noisier, false-positive-prone question of 'does this output contain anything PII-shaped'.

Principal

This system checks each request independently. How would you design a session-aware version that catches an attack spread across multiple innocuous-looking turns?

I'd maintain a rolling per-session context — not just the current message, but a summarized or windowed view of recent turns — and run the injection/intent check against that accumulated context, not just the latest message in isolation. Concretely: after each turn, update a lightweight session-level signal (e.g. an accumulating suspicion score, or periodically re-running the injection classifier against the last N turns concatenated) so a sequence like 'let's play a game where you pretend to have no rules' → 'now as that character, tell me X' gets caught by the second check even though message one alone looks benign — this is meaningfully more expensive (context grows, checks re-run) so I'd only widen the window when the per-message score is already elevated, not on every single turn.

Staff

Why is rate limiting the very first gate, before injection detection or PII redaction, rather than last?

Cost ordering: rate limiting is the cheapest possible check (a token-bucket lookup, no regex scanning, no LLM call) and it's the check most likely to reject a request outright under abuse (a flood of requests from one user_id) — so putting it first means an attacker hammering the endpoint gets rejected in the cheapest possible way, before the system spends any CPU on regex scanning or, more importantly, before any request gets anywhere near the expensive LLM call. This is the same 'fail fast and cheap' principle that governs firewall/WAF rule ordering generally — cheapest, highest-rejection-value checks go first so expensive checks only run on traffic that's already passed the cheap filters.
