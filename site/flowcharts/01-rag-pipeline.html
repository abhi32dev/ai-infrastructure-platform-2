Concrete example paths

First-ever run, no index exists yet

CLI invoked with no flags → CHECK1 is No (index doesn't exist) → full BUILDIDX chain runs (ingest→chunk→embed→index) → then ANSWER1 proceeds normally.

ENTRY → CLIMAIN → CHECK1(No) → BUILDIDX → INGEST → CHUNK → EMBED → INDEXED → ANSWER1 → RETRIEVE → ASSEMBLE → LLMCALL → GROUNDCHECK → OUTFORMAT → TEXTOUT

Second run, same index, asking an in-corpus question

CHECK1 is Yes this time (index already on disk, no --rebuild) → skips straight past the entire ingest/chunk/embed chain → retrieval finds a real match → model answers grounded, citing the source doc.

ENTRY → CLIMAIN → CHECK1(Yes) → ANSWER1 → RETRIEVE → ASSEMBLE → LLMCALL → GROUNDCHECK(Yes) → GROUNDED → OUTFORMAT → TEXTOUT

Question with no answer in the corpus (e.g. "what's the CEO's favorite color?")

Retrieval still returns something (Chroma always returns the top-k nearest vectors, even if none are relevant) — the branch that matters is entirely inside the model's response, per the system prompt's explicit instruction.

... → LLMCALL → GROUNDCHECK(No) → REFUSED → OUTFORMAT → TEXTOUT

HTTP service, forced reindex via POST /reindex

Bypasses the CHECK2 conditional entirely — /reindex calls build_index() unconditionally, regardless of whether an index already exists (this is the one place a rebuild can be forced on a running service without restarting it).

POST /reindex → app.py:reindex() → embed_index.build_index() → returns {"status": "reindexed", "vector_count": N}

What this project actually does & architecture trade-offs

What it does

  • Builds a from-scratch RAG pipeline: chunk → embed → index (Chroma) → retrieve top-k → ground-check → generate, exposed both as a CLI (pipeline.py) and a FastAPI service (app.py).
  • Decides whether to rebuild the vector index based on a content hash of the source corpus, not a blind rebuild-every-time or never-rebuild policy.
  • Refuses to answer when retrieved context has no real overlap with the query, rather than letting the LLM hallucinate a confident-sounding answer from nothing.

Known limitations

  • Single-process, single-node — no sharding, no replica set, no HA story for the vector store.
  • Ground-check is a simple heuristic (keyword/embedding-similarity threshold), not a calibrated faithfulness classifier — it can still be fooled by superficially relevant but substantively wrong context.
  • No incremental indexing: a single changed document triggers a hash mismatch and a full corpus re-embed, which doesn't scale past a small corpus.

Architectural trade-offs

  • Chose content-hash-based rebuild over a file-watcher/event-driven index because it's deterministic and testable without needing a running background process.
  • Chose a hard refuse-to-answer branch over a lower-confidence-but-still-answer approach, prioritizing precision (no hallucination) over recall (always give something).
  • Chroma (embedded, local) over a managed vector DB — zero infra cost for the portfolio, at the cost of horizontal scalability.

Principal / Staff engineer interview questions

Staff

Your index rebuild is triggered by a corpus content hash. At 10M documents, why does this design break, and what would you replace it with?

A single hash over the whole corpus means any single-document change invalidates it — at 10M docs you'd re-embed everything for a one-line edit. I'd replace the global hash with per-document content hashes stored alongside each embedding, diff the corpus against that manifest, and only re-embed the delta. That turns an O(n) full-rebuild into an O(changed) incremental update, and is the actual design most production RAG systems (e.g. incremental Chroma/pgvector upserts) use.

Staff

Walk through what happens end-to-end when a query has zero semantic overlap with the corpus — where exactly does the refusal decision get made, and why there instead of in the prompt?

Retrieval still returns the top-k nearest vectors — cosine similarity always returns something, even if everything is far away. The refusal check runs after retrieval, comparing the best similarity score against a threshold, before the context ever reaches the generator. I put it there rather than relying on prompt instructions ('say I don't know if...') because LLMs are unreliable at self-policing groundedness — a code-level gate is deterministic and testable; a prompt instruction is a suggestion the model can ignore under adversarial or ambiguous input.

Principal

If you had to scale this to serve 500 QPS with sub-200ms p99 latency, which component breaks first and what's your mitigation?

Embedding the query itself is usually the bottleneck — a local sentence-transformer call is tens of milliseconds on CPU and doesn't batch well under bursty concurrent load. I'd move query embedding to a small dedicated service with dynamic batching (or a GPU-backed endpoint), add an LRU cache keyed on normalized query text for repeat queries, and separate retrieval (cheap, sub-10ms with an ANN index) from generation (expensive, streams). Chroma itself, embedded in-process, would also need to move to a networked vector DB with replicas to survive that QPS without single-node contention.

Staff

What's the actual failure mode if two requests race to rebuild the index at the same time?

As built, there's no lock around the rebuild — two concurrent 'corpus changed' detections could both start rebuilding, doubling embedding cost and potentially leaving the on-disk Chroma collection in an inconsistent state if both writers interleave. The real fix is a rebuild lock (a lockfile or a DB-backed advisory lock) so only one rebuild runs at a time and late arrivals either wait or no-op once they see the hash already matches — this is a documented, not silently patched, gap in the current implementation.

Principal

How would you evaluate whether this RAG pipeline is actually good, beyond 'it returns an answer'?

I'd separate retrieval quality from generation quality. Retrieval: hit-rate@k and MRR against a labeled query→relevant-doc set (this is exactly what project 04's chunk-size sweep measures for a related pipeline). Generation: faithfulness (does the answer only use claims present in the retrieved context — this project's own ground-check is a cheap proxy for that) and answer relevance, ideally via a second, independent judge model (see project 02's AND-gate pattern) rather than trusting the same model's self-report.
