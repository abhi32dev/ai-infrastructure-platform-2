How the regression gate decides pass or fail

regression_gate.py:main() is the single entry point CI calls. It always runs a fresh evaluation first, then branches on whether this is a baseline-update call or a real regression check — the diagram traces every exit code and what triggers it.

Node-by-node reference

NodeLocationWhat it does
RUNEVALeval_harness.py:evaluate_and_log()Runs unconditionally, every single invocation — regardless of what happens next, MLflow gets a new logged run with this version's params/metrics.
ISUPDATEregression_gate.py:main()Checks '--update-baseline' in sys.argv. This is the one branch a human must deliberately trigger — the baseline never auto-updates on a green run, specifically to avoid slow regressions ratcheting the baseline down unnoticed.
BASEEXISTSregression_gate.py:load_baseline()First-ever run has no baseline_metrics.json yet — the code treats that as "establish it now" rather than crashing.
REGCHECKregression_gate.py:main()The actual comparison: summary.agreement_rate < baseline.agreement_rate - REGRESSION_TOLERANCE. With tolerance=0.0, this is a strict < — exactly equal or better always passes.

Concrete example paths

First run ever, no baseline file

Nothing to compare against, so this run's result becomes the baseline automatically — the only case where a baseline is written without --update-baseline.

RUNEVAL → BASEEXISTS(No) → FIRSTRUN → EXIT0B

A prompt change makes things worse

v1 scores 0.33 vs. the committed v2 baseline of 0.83 — a real regression, correctly caught and blocking the merge.

RUNEVAL → BASEEXISTS(Yes) → REGCHECK(0.33 < 0.83 → True) → PRINTFAIL → EXIT1

Deliberately promoting an improvement

An engineer runs with --update-baseline after confirming a real improvement — the new, better number becomes the committed baseline for future CI runs.

RUNEVAL → ISUPDATE(Yes) → WRITEBASE → EXIT0A

What this project actually does & architecture trade-offs

What it does

  • Runs an MLflow-backed regression gate in CI: every run logs metrics, then compares this run's agreement_rate against a committed baseline, failing the build if it regressed.
  • Separates baseline updates (requires an explicit --update-baseline flag) from baseline checks (automatic, every CI run) so the baseline never silently ratchets down.
  • Handles the first-run-ever case by establishing the baseline automatically rather than crashing on a missing file.

Known limitations

  • Regression is judged on a single scalar metric (agreement_rate) with zero tolerance — no statistical significance testing, so a run that's worse by noise alone can fail the build.
  • The baseline file is a single JSON file in the repo, not versioned per-model or per-environment — there's no way to track multiple concurrently-valid baselines (e.g. one per deployment target).
  • No automatic rollback or alerting integration — a failed gate just exits non-zero; a human still has to notice and act.

Architectural trade-offs

  • Zero-tolerance strict comparison (REGRESSION_TOLERANCE = 0.0) over a noise-band threshold — chosen for simplicity and to force explicit human judgment on any regression, at the cost of possible false-positive CI failures on borderline noise.
  • Human-gated baseline promotion over auto-promotion-on-green — deliberately slower, to prevent a slow-bleed regression from ratcheting the baseline downward unnoticed over many small merges.
  • MLflow local tracking store over a hosted MLflow server — zero infra cost for the demo, at the cost of no team-wide shared run history.

Principal / Staff engineer interview questions

Staff

Your regression check uses a strict `<` comparison with zero tolerance. What's the actual failure mode of that design in a noisy CI environment, and how would you fix it without losing the safety property?

With zero tolerance, any run that scores even 0.0001 below baseline fails — including pure evaluation noise from nondeterministic model sampling or dataset ordering. I'd replace the point comparison with a statistical test: run the eval multiple times (or bootstrap the existing eval set), compute a confidence interval on the agreement rate, and fail only if the new run's upper bound is below the baseline's lower bound minus a tolerance band. That's a direct application of the same significance-testing logic project 07 builds standalone — the two projects should really share that harness.

Principal

Why is baseline promotion a manual flag instead of automatic on a green build — isn't that just adding toil?

It's a deliberate asymmetry: auto-promoting on every green run means a sequence of many tiny, individually-non-significant regressions can compound into a large one with zero human ever reviewing the trend — 'boiling frog' baseline decay. Requiring --update-baseline forces a human (or a separate, explicitly-reviewed promotion job) to look at the number and decide it's a real improvement worth committing as the new floor. The toil cost is one flag on genuine improvements; the risk avoided is silent, cumulative quality decay in a metric nobody's watching closely enough to catch increment-by-increment.

Staff

This gate only tracks one metric. In a real system you'd have latency, cost, and multiple quality metrics. How would you extend this without turning the gate into an unmaintainable pile of if-statements?

I'd generalize load_baseline()/the comparison function to take a list of metric specs — each with its own comparison direction (higher-is-better vs lower-is-better), tolerance, and severity (hard-fail vs warn-only) — and iterate over them, collecting all violations before failing, rather than the current single hard-coded comparison. This is the same pattern real gating tools (e.g. Great Expectations, or a custom metrics-contract YAML) use: data-driven checks over hard-coded conditionals, so adding a new metric is a config change, not a code change.

Principal

The baseline is a single JSON file in the repo. What breaks when you need per-environment baselines (staging vs prod) or per-model-variant baselines, and how would you redesign the storage?

A flat file with no namespacing means two teams or two environments would either clobber each other's baseline or need entirely separate copies of this whole pipeline. I'd move the baseline into MLflow's own model registry as a tagged/aliased run (e.g. an MLflow Model Version alias like champion per environment), so 'what's the current baseline for staging' is a registry query, not a file path convention — and promotion becomes a registry API call with full history, rather than an overwritten JSON file with only git history to fall back on.

Staff

What's the actual bug class this gate is designed to catch that a normal unit test suite wouldn't?

Unit tests catch functional regressions — code that crashes or produces the wrong type/shape. This gate catches quality regressions — code that runs fine and produces plausible-looking output, but is measurably worse against real evaluation data (e.g. a prompt tweak that quietly drops agreement rate). That class of bug is invisible to assertion-based tests because there's no single 'correct' output to assert against — only a statistical property of many outputs, which is exactly what a regression gate against a logged metric baseline is built to detect.
