Which statistical test runs, and how significance gets decided

Two test families exist for a reason — binary outcomes need a two-proportion z-test, continuous measurements need Welch’s t-test. The diagram shows how each computes its p-value, and the one line (bool(p_value < 0.05)) that decides everything downstream.

What this project actually does & architecture trade-offs

What it does

  • Implements two real statistical tests from scratch semantics — a two-proportion z-test for binary outcomes, and Welch's t-test for continuous measurements — with an explicit bool(p_value < 0.05) significance decision.
  • Recovers a real, seeded 7.4% relative lift from 50,000 simulated users per arm, proving the z-test correctly detects a true effect at scale.
  • Correctly refuses to call a dramatic-looking 56% latency difference significant when it's really outlier-driven noise from a tiny (n=8) sample.

Known limitations

  • Fixed significance threshold (0.05) with no multiple-testing correction — running many simultaneous A/B tests with this harness would inflate the false-positive rate without a Bonferroni/FDR adjustment.
  • No sequential testing support — a real experimentation platform needs to handle 'peeking' at results before the planned sample size is reached without inflating false positives, which this harness doesn't address.
  • No effect-size/practical-significance reporting alongside statistical significance — a p<0.05 result with a trivially small effect size would still be flagged 'significant' here.

Architectural trade-offs

  • A fixed 0.05 threshold and one-shot testing over sequential/Bayesian testing — simpler to implement and explain, at the cost of the 'peeking' problem and no early-stopping efficiency.
  • Welch's t-test (unequal variance assumed) over Student's t-test — more robust to the common real-world case of two arms with genuinely different variances, at a small cost in statistical power when variances actually are equal.
  • An explicit bool() wrap on the significance check over trusting numpy's boolean type directly — a real bug (a numpy bool failing an is True check in a test) forced this, prioritizing test-suite correctness over what looked like unnecessary defensive code.

Principal / Staff engineer interview questions

Staff

You found a real bug where a numpy bool failed an `is True` check. Walk through exactly why that happens and why the fix is `bool()` rather than fixing the test.

numpy.bool_ (what comparisons on numpy arrays/scalars return) is a distinct type from Python's built-in bool — np.True_ == True is True, but np.True_ is True is False, because is checks object identity, not equality, and numpy's boolean is a different singleton than Python's. The right fix is at the boundary where the function's public contract is defined — explicitly casting to Python bool() before returning — because callers (including test code) reasonably expect a public API's boolean return value to behave like a normal Python bool, including under identity checks; patching the test to use == instead just hides the type leak rather than fixing it.

Principal

You have no multiple-testing correction. If a team runs 20 simultaneous experiments through this harness, what's the actual mathematical consequence, and how would you fix it?

With no correction, each test's 5% false-positive rate compounds independently — the probability that at least one of 20 truly-null experiments shows a false 'significant' result is roughly 1 − 0.95^20 ≈ 64%, not 5%. I'd add a correction layer over the existing per-test p-values: Bonferroni (divide alpha by the number of concurrent tests) for a conservative, simple fix, or Benjamini-Hochberg FDR control if the team runs many tests routinely and can tolerate a controlled false-discovery rate rather than a strict family-wise error rate — the choice depends on whether false positives or reduced power is the more expensive mistake for that team.

Staff

Your Welch's t-test example correctly refuses to call an 8-sample, outlier-driven 56% difference significant. What would you tell a PM who says 'but the number is right there, 56% faster' and pushes to ship anyway?

I'd show them the actual data: one cold-start outlier is dominating both arms' means at n=8, and the confidence interval on the difference is wide enough to include zero — meaning the true effect could be anywhere from a real win to a real loss, and this sample simply can't tell them which. The right response isn't 'ignore the number', it's 'the sample size is too small to trust this number' — I'd recommend collecting enough additional samples to shrink the CI to a decision-useful width (a power analysis can give the exact n needed) before making a ship/no-ship call on the metric.

Principal

How would you redesign this harness to support sequential testing — stopping early when a result is clearly significant, without inflating the false-positive rate the naive way people usually get this wrong?

Naive early-stopping (check p-value after every batch, stop as soon as p<0.05) inflates false positives because you're effectively running many correlated tests and taking the best result — the 'peeking problem'. I'd implement a proper sequential testing method — either a Sequential Probability Ratio Test (SPRT) with pre-specified error-rate bounds, or an always-valid p-value / confidence sequence approach (e.g. what Optimizely and other real experimentation platforms use) — which is specifically designed so that checking the result at any time, including continuously, doesn't inflate the overall false-positive rate the way naive repeated significance testing does.

Staff

The z-test pools both arms' successes to compute standard error. What assumption does that rely on, and when would it give you a wrong answer?

Pooling assumes the null hypothesis is true when computing the standard error (i.e. it estimates variance under 'both arms have the same true rate'), which is the standard, correct approach specifically for testing whether two proportions differ — it's what makes it a valid hypothesis test rather than just a confidence-interval comparison. It would give a misleading answer if you used the pooled standard error to also construct a confidence interval on the difference between the two rates (rather than just the significance test) — for that you'd want the unpooled standard error, since you're no longer assuming the null is true, you're trying to estimate the actual size of a possibly-nonzero difference.
